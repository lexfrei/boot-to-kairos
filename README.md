# boot-to-kairos

boot-to-kairos turns a running Linux machine into [Kairos](https://kairos.io) from userspace. You don't need a rescue system or a custom ISO. The idea comes from [boot-to-talos](https://github.com/cozystack/boot-to-talos).

This is early work, tested on a few setups only (see below). It erases the target disk.

## How it works

1. It fetches the Kairos OCI image, from a registry or from a file on the machine, and unpacks it into a tmpfs. Before any layer is downloaded, it verifies the image's cosign signature, and refuses an image without one from Kairos (see [Signature](#signature)). Each layer is first copied to the tmpfs and checked against its digest, and only then unpacked, so a layer that does not match is refused before any of it is applied. With `--workdir` the layers are staged on another disk instead (see [Work dir on another disk](#work-dir-on-another-disk)).
2. It attaches a sparse file the size of the target disk, in the tmpfs or in `--workdir`, as a loop device and runs the image's own `kairos-agent manual-install` on it, from a chroot of the image. Commands the agent would run against the whole host, `blkdeactivate` and a reboot or poweroff asked for in the config, are replaced with ones that do nothing, and it sees a blank kernel command line instead of the host's, from which it would merge install settings and run stages. You get what that image's installer would give you: active, passive and recovery systems, and a persistent partition over the rest of the disk.
3. Until this point the running system is not touched, with one exception: the agent runs `udevadm trigger`, which replays device events host-wide, so udev rules on the host run again and may, for example, activate an LVM volume group left inactive. Everything above runs in a mount namespace of its own, so nothing it mounts reaches the rest of the system, and all of it goes away once the installer and whatever it started have exited, however they exit.
4. It turns off the swap on the target disk, partitions and files alike, and freezes every filesystem on it, so nothing writes to the disk anymore. A filesystem that cannot be frozen, like the vfat ESP, is remounted read-only instead. If any of this fails, or the first write attempt fails before its first byte, what was done is undone and nothing is written. If the undo itself fails, it stops with a message that a filesystem may still be frozen and that you should reboot.
5. It copies the file over the disk. Data is copied and holes are zeroed. Then it reads the disk back, bypassing the page cache, and writes again any page that differs. If that fails, it tries the whole write again, three attempts in all. The machine sits frozen while the whole disk is written and read back, which on a large HDD takes a long time. Do not reset it.
6. It flushes the filesystems on other disks, each on its own so the old ones on the target disk stay untouched.
7. On a UEFI machine it writes a UEFI boot entry for Kairos and puts it in the boot order where the old system stood (see below). Then it reboots into Kairos.

It reboots through the firmware, not with kexec into the new kernel, on purpose: that first boot proves the firmware boots the disk the same way every later boot will, from the boot entry it wrote or, without one, from its fallback to `\EFI\BOOT`, and on legacy BIOS from the boot sector the image put on the disk. The price is one POST.

## UEFI boot entry

Once the disk is written and verified, a boot entry named `Kairos` is written to the firmware's NVRAM through efivarfs. It loads `\EFI\BOOT\BOOTX64.EFI` (`BOOTAA64.EFI` on arm64, `BOOTRISCV64.EFI` on riscv64), the shim the image installs, from the new EFI system partition, which it names by the partition GUID in the new partition table. If an identical entry exists, it is reused.

Entries that point at a partition of the replaced disk are removed, together with a `BootNext` that names one: after the write those partitions are gone. A partition is recognised by its GPT partition GUID, or by the disk signature on an MBR disk, both read before the disk is overwritten. Another disk cloned from the target without new GUIDs or signature looks the same, and its entries go too; the firmware cannot tell such disks apart either. If the NVRAM is full, the old entries are removed first to make room.

In `BootOrder` the new entry takes the place of whichever comes first, an old entry or the reused one, so the firmware does not have to fall back to the disk's default loader on its own, and a machine set to boot from the network first, as provisioning systems do, still does when the old system had an entry of its own. Only when `BootOrder` named none of them does the new entry go first. Entries for other disks, network boot and the firmware's own entries keep their order.

Nothing in NVRAM changes unless the disk was written and read back without error. The build does not see the firmware's variables at all: inside its chroot efivarfs, and the older sysfs interface at `/sys/firmware/efi/vars` that kernels before 6.0 also offer, are covered by an empty read-only tmpfs, so a boot entry written by kairos-agent or a cloud-config stage fails instead of reaching NVRAM before the disk is verified. A stage that mounts efivarfs or sysfs again on its own is not stopped. If writing the entry fails after that, the error is logged, the machine still reboots, and the firmware has to fall back to the same loader under `\EFI\BOOT` on the disk, as OVMF does and some firmware may not. Without efivarfs mounted read-write at `/sys/firmware/efi/efivars` no entry is written, and a warning says so before the disk is touched.

## Requirements

- Root on a UEFI machine, or on an x86-64 machine with legacy BIOS. Kairos is installed for the mode the running system booted in, so a UEFI machine booted through its legacy BIOS compatibility mode gets a legacy BIOS install and has to stay in that mode.
- Free RAM for the build. `quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0` needs about 2.6 GiB available: the unpacked image, about 330 MiB, with 256 MiB of headroom, the 1483 MiB disk image, the 64 MiB the build must leave free in the tmpfs (see [Work dir on another disk](#work-dir-on-another-disk)), and the 512 MiB reserve below. The build itself peaked at 1.77 GiB. The build uses what is available when it starts, less 512 MiB left to the rest of the system, and stops with an error before touching the disk if that is not enough. Each layer is held in the tmpfs as stored, compressed or not, until it is unpacked, and counts against the same memory. For that image this raised the peak while unpacking without raising the peak of the whole build: sampling Shmem in `/proc/meminfo` about every 0.1 s while installing it on a 6 GiB VM, unpacking peaked at 377 MiB, against 319 MiB when each layer was streamed straight into the tmpfs, and the whole build at 1.77 GiB either way. A layer that would not fit beside what is already unpacked is refused before it is downloaded, and the unpacked image may then grow only into what the layer leaves. Before anything is downloaded, an image that would be refused or run out of room that way even if no layer unpacked to more than its stored size and none replaced or deleted what an earlier one unpacked is refused too. With `--workdir` only the unpacked image stays in RAM: it must fit in the same budget with 256 MiB of headroom, and installing that image on the same VM, Shmem peaked at 329 MiB, so about 1.1 GiB available is enough. The arm64 image of the same release, `quay.io/kairos/hadron:v0.5.1-core-arm64-generic-v4.3.0`, made a 1624 MiB disk image instead of 1483 MiB, so it needs about 140 MiB more for the disk image alone.
- A Kairos image for the host's architecture that ships `kairos-agent`.
- With Secure Boot on, an image whose boot chain this firmware trusts. Once the disk image is built, the installer reads what the firmware would load from it: `\EFI\BOOT\BOOTX64.EFI` (`BOOTAA64.EFI` on arm64) from the new EFI system partition, the GRUB beside it when that loader is shim, and the image's `/boot/vmlinuz`. It looks up each one's Authenticode hash and the certificates of its signatures in the firmware's db and dbx, in the shim's own vendor certificate and deauthorized list, and in the MOK lists the running system's shim left in `MokListRT` and `MokListXRT`. If the firmware or shim would refuse one of them, the install stops with class `secure-boot` before the disk is touched, naming the file and why; so it does when Secure Boot is on and those lists cannot be read through efivarfs, or do not parse. `quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0` is refused: its shim, GRUB and kernel carry no signature. An image built with kairos-init from Ubuntu carries Ubuntu's shim, signed by Microsoft, and GRUB and kernel signed by Canonical, and passes on firmware with Microsoft's keys. Keys cannot be enrolled from the running system, as MOK enrollment needs a reboot and a confirmation at the console, so use an image signed for this firmware or turn Secure Boot off in its setup. The variables are read from efivarfs, or from `/sys/firmware/efi/vars` when efivarfs is not mounted. That interface hands out at most 1024 bytes of a variable, which db and dbx usually exceed, so through it Secure Boot may be found on and its lists not read; the install then goes ahead without the check, with a warning to mount efivarfs. On a UEFI machine where neither interface is there it goes ahead with a warning too. Legacy BIOS has no Secure Boot and is not checked.
- A way to log in to the installed system: the SSH logins carried over from this one (see [Identity](#identity)), or a cloud-config that sets one up, for example a user with an SSH key.

## Install

Each release has static binaries for linux/amd64 and linux/arm64 and a `SHA256SUMS` file. Replace `vX.Y.Z` with the release you want:

```bash
VERSION=vX.Y.Z
ARCH=amd64 # or arm64
curl --fail --location --remote-name-all \
  "https://github.com/lexfrei/boot-to-kairos/releases/download/$VERSION/boot-to-kairos-linux-$ARCH" \
  "https://github.com/lexfrei/boot-to-kairos/releases/download/$VERSION/SHA256SUMS"
sha256sum --check --ignore-missing SHA256SUMS
chmod +x "boot-to-kairos-linux-$ARCH"
mv "boot-to-kairos-linux-$ARCH" boot-to-kairos
./boot-to-kairos --version
```

## Usage

```bash
cat > config.yaml <<'EOF'
#cloud-config
users:
  - name: kairos
    groups: [admin]
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... you@example.com
EOF

sudo ./boot-to-kairos \
  --image quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0 \
  --disk /dev/sda \
  --cloud-config config.yaml
```

The image must be built for the machine's architecture; on arm64 that is `quay.io/kairos/hadron:v0.5.1-core-arm64-generic-v4.3.0`. One for another architecture is refused before any of its layers is downloaded (see [Image](#image)).

A user the cloud-config creates without `passwd` or `lock_passwd: true` gets an empty password, which the console accepts, as the image's PAM allows empty passwords; sshd does not. `kairos` keeps the locked password the image gives it, but `lock_passwd: true` costs nothing there either.

While the identity is carried over, `--cloud-config` is optional (see [Identity](#identity)).

`--disk` also takes a link like `/dev/disk/by-id/...`. Without `--yes` it asks you to type the disk path before it starts, and for a link that is the kernel name it resolves to, like `/dev/sda`. A second instance refuses while one holds `/run/boot-to-kairos.lock`; versions from before this lock was added do not take it.

### Work dir on another disk

`--workdir DIR` builds the disk image in an existing directory `DIR` on another disk instead of in RAM. The build makes `DIR/boot-to-kairos`, keeps the disk image and each layer, until it is unpacked, in it, and removes it again when it stops, whether it refused, failed or wrote the disk; after a write, before it flushes the other disks, so the image does not stay behind on them. A write that fails after touching the disk keeps the disk image, and the error says where: writing it over the disk from rescue media finishes the install. The unpacked image stays in a tmpfs at `/run/boot-to-kairos`, and the lock stays at `/run/boot-to-kairos.lock` with or without the flag. For that image the disk image took 1483 MiB of `DIR`.

The disk image is read from `DIR` while the target disk is written over, after its filesystems are frozen, so `DIR` is refused, before anything is downloaded, when:

- it is on the target disk: on any of its partitions, or on LVM, dm-crypt, md or a btrfs filesystem with a device on it. Freezing the target would stop the build's own reads, and the write would overwrite what it reads from;
- its filesystem is served by a FUSE daemon, sshfs and the like but also ntfs-3g and exfat-fuse on a local disk, or is not on a local block device: NFS, CIFS, tmpfs and overlay. A FUSE daemon or a kernel upcall paged in from the frozen disk would block for good, and a network that drops would leave the disk half written;
- it is on a block device that may read over the network, for the same reason: nbd, rbd, iSCSI, ATA over Ethernet, DRBD, and NVMe whose controllers are not all PCIe (NVMe over TCP, RDMA or Fibre Channel);
- its devices include a loop device backed by a file: where that file lives cannot be told, and it may be on the target disk;
- it does not keep sparse files, as vfat and exfat do not, or cannot hold a file the size of the disk: the disk image is as large as the disk. A file truncated to 16 MiB must stay unallocated and read as a hole, and must then grow to the size of the disk;
- `DIR/boot-to-kairos` exists. It is left by a run that did not finish and holds only that run's disk image and staged layers: remove it.

The free space of `DIR` is checked before each layer is staged and, once the image is unpacked, against what the disk image may come to: kairos-agent sizes its active, passive and recovery images each to the unpacked image plus 100 MiB, mke2fs gives the persistent partition a journal of 1/256 to 1/128 of it, from 64 MiB up to 1 GiB, of which the estimate takes 1/128, and 256 MiB is added for the rest. This is an estimate. The loop device writes the disk image back on its own, so a write that found `DIR` full may not fail the agent: a build that leaves less than 64 MiB free in `DIR` stops with `not-enough-space` before the disk is touched, and in the tmpfs, without `--workdir`, with `not-enough-memory`.

### Dry run

```bash
sudo ./boot-to-kairos \
  --image quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0 \
  --disk /dev/sda \
  --cloud-config config.yaml \
  --dry-run
```

`--dry-run` does everything up to the point of no return: every check and refusal, the network capture and its refusals (see [Network](#network)), the image download, with the memory checks before it, and the full build of the disk image with the image's `kairos-agent`, and the resolution of what the quiesce would stop. Then it stops, without asking, before turning off swap or freezing anything, and prints the plan to stdout in the order the install worked it out: the image, the work dir (see [Work dir on another disk](#work-dir-on-another-disk)), the network it would carry over (the files it writes and the static addresses and routes they set, or why it carries none), the hostname, SSH host keys by fingerprint and SSH users it would carry over and what it leaves out (see [Identity](#identity)), whether the cloud datasources are off (see [Cloud datasources](#cloud-datasources)), the target disk with its size and sector size, where the image was read from with the digest of the manifest picked for this architecture and the number and stored size of its layers, the signature it verified, or that it verified none, whether Secure Boot is on and, if it is, who signed each file of the boot chain and which key or hash entry trusts it, or why that could not be checked (see [Requirements](#requirements)), how much of the disk image the build filled, the firmware mode the machine booted in, the boot entry it would write (see [UEFI boot entry](#uefi-boot-entry)) or, on legacy BIOS, that there is none, the swap areas it would turn off and the filesystems it would freeze or remount read-only. The disk, its swap, its filesystems and the firmware's NVRAM are left alone, apart from what the cloud-config's own install-time stages do (see [Limitations](#limitations)), and what the build mounted goes away with its mount namespace. It exits with 0 when every check before the point of no return passes, and with the refusal otherwise. A passing dry run does not promise a passing real run. Three things it cannot try can still stop the real run: turning off swap, which pulls its pages back into the memory the build filled; a freeze or read-only remount; and a first write attempt that fails before it writes anything. The real run then handles them as step 4 describes. Like the real run, it lets the agent run `udevadm trigger` (see step 3 above).

### Output for automation

With `--output json`, stdout carries a single JSON object and nothing else; logs and the confirmation prompt go to stderr. A dry run prints it at the end. A real run prints it right before the point of no return, or at the refusal if it stops before that; its `passed` covers the checks up to that point, and what happens after it shows only in the exit status and on stderr. Past the point of no return stdout may be a file on the frozen disk, so from there on only stderr and the kernel log (`/dev/kmsg`) get anything.

```json
{"dryRun":true,"passed":true,"plan":[{"name":"image","value":"quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0"},{"name":"swap to turn off","values":["/swap.img"]}],"refusal":null}
```

`plan` lists the items in the order the text output does; an item has `value`, or `values` when it is a list. `refusal` is `null` when every check passed, and otherwise has the message and a `class`: `usage`, `not-whole-disk`, `bad-config`, `bios-unsupported`, `label-clash`, `aborted`, `not-enough-memory`, `not-enough-space` for a `--workdir` that is too full, `bad-workdir` for one refused as above, `secure-boot` for an image whose boot chain Secure Boot would refuse, or for Secure Boot whose lists cannot be read through efivarfs or do not parse (see [Requirements](#requirements)), `already-running`, `disk-in-use`, `network-unsupported`, `no-login`, `account-clash`, `interrupted`, `bad-image` for an image that cannot be used as given (none for this architecture, a digest that does not match, more than one candidate in a layout, a legacy docker save archive, a registry redirect to plain http, or an EFI system partition built for the disk that UEFI firmware cannot read, see [Limitations](#limitations)), `no-signature` for an image without a signature, `bad-signature` for one whose signature does not verify or is not by the expected signer (see [Signature](#signature)), or `error` for anything else.

Errors before the installer itself starts, flags it cannot parse, not running as root and a failure to set up its mount namespace, print no object. Exit status, in either output mode: 0 when a dry run passed; 1 when it refused, or when a real run refused or failed (a real run that succeeds reboots and never exits); 2 for flags it cannot parse; 128 plus the signal number when the installer was killed by a signal.

## Image

`--image` takes a registry reference, or an image already on the machine, for an install without network access:

- `oci:DIR` reads an OCI image layout directory, as `skopeo copy docker://IMAGE oci:DIR` writes it.
- `oci-archive:FILE` reads the same layout from a tar archive, as `skopeo copy docker://IMAGE oci-archive:FILE`, `podman save --format oci-archive` and `docker save` from Docker 25 on write it. The archive is read in place, not unpacked first.

None of these copies the image's signature, so such an image is refused unless it was copied with its signature as [Signature](#signature) describes, or `--verify-signature=false` is given.

A reference after the path, as in skopeo's `oci:DIR:TAG`, is not supported: the whole value is taken as the path.

A local image is checked like a pulled one: the manifest, the config and every layer must match the digests the index names, or the install stops before that layer is applied. From a multi-architecture index the host's architecture is picked, and the image's config must name that architecture too, so a single-architecture image built for another one is refused, from a registry as well. A layout holding more than one image for the host's architecture is refused rather than guessed, as is one with an image for that architecture, or without a platform, that cannot be read, which might have been another match: copy the one you want into a layout of its own.

From a registry each layer is downloaded whole, checked, then unpacked. A download that breaks off, receives nothing for a minute, gets a 5xx, 408 or 429 answer, or does not match its digest is tried again, five attempts in all, waiting 1, 2, 4 and 8 seconds in between. Any other answer, such as not found or unauthorized, stops the install at once, and so does a certificate the machine does not accept. A pull-through cache that sends nothing of a layer until it has fetched the layer itself must start sending within that minute, or the attempt is counted as stalled.

Nothing goes to a registry over plain http unless it is at a loopback address such as `127.0.0.1:5000`; `localhost` is a name, which DNS may resolve elsewhere. Over plain http anyone on the path could hand over another manifest for the tag, and every digest checked after comes from it. Where the client would fall back to http, for a registry at a private address or under a `.local` name, or fetch a token from an http URL, it asks over https instead, so a private registry with a certificate the machine accepts works as usual and one without it fails like any https error. A redirect to plain http is refused, including one for a layer. `--insecure-registry` allows plain http to any registry, and the plan's image source then says so.

### Signature

The image's cosign signature is verified once its manifest is resolved, before any layer is downloaded, and an image without a signature that verifies is refused. The digests prove that the bytes match the manifest; the signature proves that the manifest is one Kairos released, which neither a replaced tag nor a registry serving something else can fake. An image that is merely unsigned is refused as well: whoever can replace a tag can push the replacement without a signature.

By default the signature must come from Kairos's release pipeline: a GitHub Actions workflow of `kairos-io/kairos`, or of `kairos-io/kairos-factory-action` for releases before v4.3.0, run for a release tag of `kairos-io/kairos`. Kairos signs the index of each release image keyless through Sigstore, as a sigstore bundle attached as an OCI referrer from v4.3.0 on, and as a `.sig` tag before; both are read, the `.sig` tag when no bundle is a signature, as when the only ones attest something else. When `--image` names a tag, the release the signature was made for must be one of its dash-separated parts, the last or one followed by more, as `v4.3.0` is in `v0.5.1-core-amd64-generic-v4.3.0`, so an older release, signed just as well, is refused under a newer release's tag. The signature does not cover the tag itself, so two flavors of one release for the same architecture, such as `generic` and `rpi4`, cannot be told apart by it. A digest reference is verified too, without the tag check. Kairos signs the index only, not the manifest for each architecture inside it, so pin the digest of the index: a pinned per-architecture manifest is refused as unsigned.

The signature is looked up for the digest the registry returned for the reference, not by resolving the tag again, and fetched like the image, with the same rules for plain http and retries, each attempt dropped as stalled after a minute; with `--insecure-registry` it is what still stands between the install and an image swapped on the way. A mirror or pull-through cache that does not keep the signature, the referrer or the `.sig` tag, gets the image refused as unsigned.

Verifying needs Sigstore's trusted root, which is fetched from its TUF repository, `https://tuf-repo-cdn.sigstore.dev`, over https whatever `--insecure-registry` says, each file within a minute, and kept in memory only. Rekor is not asked: the signature carries its log entry. A machine that cannot reach the TUF repository needs `--trusted-root FILE`, a `trusted_root.json` such as the one `cosign initialize` leaves under `~/.sigstore/root/tuf-repo-cdn.sigstore.dev/targets/` on a machine that can.

An `oci:` or `oci-archive:` image is verified against the sigstore bundles it holds as referrers of the image, listed in its `index.json`, as `oras copy --recursive IMAGE --to-oci-layout DIR:TAG` writes them; copy the whole index, without `--platform`, as only the index is signed, and pack the directory with `tar --create --file FILE --directory DIR .` for `oci-archive:`. A legacy `.sig` signature is not read from a layout. A layout carries no tag, so the tag check does not apply; the plan names the release the signature is for.

`--verify-signature=false` installs the image without any of this, and the plan says so. To accept another signer, for an image you build and sign yourself, pass `--signature-identity`, a regular expression the identity in the signing certificate must match, and `--signature-issuer`, the OIDC issuer it names, as `cosign verify` takes `--certificate-identity-regexp` and `--certificate-oidc-issuer`. The expression matches anywhere in the identity unless anchored, so write `^https://github\.com/you/repo/` rather than `github.com/you/repo`, which an identity under another account can contain. The checks on Kairos's repository and release then do not apply. Signatures made with a key rather than a Sigstore certificate are not accepted.

## Network

Kairos brings every Ethernet NIC up with DHCP by default. A machine reachable only at a static address, or only through a bond, a VLAN or a bridge, would not come back on the network after the reboot, so boot-to-kairos carries the running system's network configuration over, unless you pass `--keep-network=false`.

It reads the configuration from the kernel, not from the old system's configuration files: addresses, routes, MTUs, bonds, VLANs and bridges, and the nameservers and search domains from `/etc/resolv.conf` (or, behind systemd-resolved's local stub, from the upstream list resolved keeps in `/run/systemd/resolve/resolv.conf`). It adds a stage to the cloud-config that writes systemd-networkd files on every boot, as Kairos writes its own default configuration, so the configuration survives upgrades. NICs are found by their burnt-in MAC address, so it does not matter that Kairos names them differently.

- An address without a lifetime is written as static, unless a DHCP client owns it. An address with a lifetime came from DHCP or SLAAC. So did an IPv4 address that a lease records: networkd's lease in `/run/systemd/netif/leases`, or, while a DHCP client is running, an unexpired NetworkManager, dhclient or dhcpcd lease under `/var/lib` for that very address. A lease file left from before the address was made static therefore does not count once its client is gone. A dhclient, dhcpcd or udhcpc running for a NIC with no lease to read owns all of the NIC's IPv4 addresses. A NIC with a lease keeps DHCP for IPv4, and router advertisements still configure IPv6. A client started without naming the NIC and without a lease file is not detected, and its addresses are written as static.
- Routes the system's network configuration set up (`proto boot` and `proto static`) in the main table are carried, source-specific ones with their source. On the carried interfaces, routes from a routing daemon, routes in other tables and routes of types other than unicast are not, and the installer names them; policy routing rules are not carried either. A default route from a routing daemon refuses the install, as without the daemon the installed system would be reachable from its own subnets only: configure such a host's network in the cloud-config. A prefix route that NetworkManager installs beside its addresses comes back with its metric. A `proto boot` route through the gateway of a DHCP lease, which dhclient-script and udhcpc install that way, is left to DHCP; where a DHCP client runs for an interface with no lease to read, so is every `proto boot` IPv4 route through a gateway on it, hand-added ones included, as the two look the same.
- A NIC that only uses DHCP, at the default MTU, outside any bond, VLAN or bridge, is left to Kairos's default configuration.
- Bonds, VLANs and bridges are recreated with their MAC addresses and with every parameter that differs from the kernel's default. A parameter systemd-networkd cannot set refuses the install, with its name, rather than being dropped.
- Interfaces with no NIC under them, such as container bridges, VPN tunnels or a bridge's tap ports, are left out.
- Team devices, Open vSwitch, VRFs, macvlan, ipvlan, other tunnel devices bound to a NIC, Wi-Fi, and NICs that are not Ethernet are refused when a NIC is at or under them: nothing is written, and the error names the interface. So are multipath routes and routes over nexthop objects that the network configuration set up, bridges with VLAN filtering, VLAN priority maps and two NICs with the same MAC address.
- A virtual function its driver pairs with a NIC, as on Azure, is left to that driver: the NIC's file matches its driver as well as its MAC address, which the two share. Where the driver does not tell them apart either, as with virtio's net_failover, the install is refused.

If the cloud-config configures the network itself, writing files under `/etc/systemd/network/`, `/run/systemd/network/`, `/etc/systemd/resolved.conf*` or `/etc/resolv.conf`, setting `dns` in a stage, or passing `ip=` in `install.grub_options`, nothing is carried and the cloud-config's configuration applies alone. networkd uses the first file matching a NIC, so a carried file could silently override part of yours. What a stage's `commands` do is not checked.

## Identity

Kairos builds its users from the image on every boot, generates new SSH host keys on the first one and names itself `kairos-` and four characters of its machine ID. So boot-to-kairos carries over who can log in over SSH, the SSH host keys and the hostname, unless you pass `--keep-identity=false`. Clients then reach the same name with the same key and see no host key change.

- Users are the accounts in `/etc/passwd` whose shell is not `nologin` or `false` and that have keys in the files the host's sshd reads: its `AuthorizedKeysFile` from `sshd -T`, or `.ssh/authorized_keys` and `.ssh/authorized_keys2` when that cannot be read. Match blocks are not evaluated, so a file that only a `Match` block names is not read, and a `ForceCommand` or `ChrootDirectory` a `Match` block puts on a user does not come along. Keys an `AuthorizedKeysCommand` serves are not carried, and the plan says so. Accounts that only LDAP or another NSS source knows are not seen.
- Each comes back under the same name, with its key lines as they are, options included, and with its password locked: passwords are not carried. It is in Kairos's `admin` group, whose members may use sudo without a password, when it was in `sudo`, `admin` or `wheel`, or when sudoers let it run a shell as root. Its other groups are not carried, and its shell is `/bin/bash`; a user with a restricted shell such as `git-shell` or `rbash` is not carried. To give such a user a password, configure it in the cloud-config; its keys then come from the cloud-config alone.
- The carried keys are added again on every boot, as Kairos rebuilds its users from the image. To revoke one, remove it from `/oem/90_custom.yaml`, not only from `~/.ssh/authorized_keys`. Kairos's sshd allows two authentication attempts per connection, so a client that offers several keys before the right one is refused with "Too many authentication failures"; point it at the key with `-i` and `IdentitiesOnly yes`.
- Kairos's sshd refuses root logins. When no carried admin user can log in, root's keys go to the image's `kairos` user, in `admin`, so the same key keeps working and only the login name changes. A key with a forced command, like the "login as ubuntu" lines of cloud images, never moves. When a carried admin user can log in, root's keys are not carried. A host user named `kairos` is carried only when it could use sudo here, as Kairos's `kairos` is always in `admin`.
- Left out, each named in the plan: key types Kairos's sshd does not accept (DSA, which OpenSSH 10 removed, and unknown ones), lines Kairos would fetch as a URL, anything containing `{{` or `}}`, which yip renders as a template in files, commands and conditions, and names that are not lowercase POSIX user names or that the image uses for a user or a group, `admin` included: yip would give such a user a group of that name, written over the image's own. Names an image other than Hadron uses are found once the build has unpacked it, which then stops with class `account-clash`.
- Host keys are the ones the host's sshd uses (`HostKey`), RSA, ECDSA and ed25519, each with its `.pub`. Each is written at boot only where Kairos has none of its type yet, before Kairos would generate one, so a key rotated later stays. Kairos's sshd offers ed25519 and RSA host keys only, so a client that knows the host by its ECDSA key alone refuses the new system; the installer warns about it. The fingerprints the plan shows are read from the `.pub` files, which are not checked against the private keys. No host key is carried when a debug log would print them: `debug` in the cloud-config, or `debug`, `rd.kairos.debug` or `rd.immucore.debug` in its `install.grub_options`, which puts them on every boot of the new system. This system's own kernel command line does not count: the build's kairos-agent sees a blank one.
- The hostname is the kernel's, unless it is empty or `localhost`.

Without `--cloud-config`, the install goes ahead only when a carried admin user has a key without a forced command, and refuses with class `no-login` otherwise, before anything is built.

What the cloud-config sets itself wins: a user it names in `users`, or in a stage's `users` or `authorized_keys`, is not carried, nor is the hostname when it sets `hostname` or writes `/etc/hostname`, nor any host key when it writes a file under `/etc/ssh/ssh_host_`.

The private host keys end up in the cloud-config that kairos-agent stores as `/oem/90_custom.yaml` on the OEM partition, mode 0640, owner root and group `admin`, whose members are root through sudo anyway, and in `/etc/ssh` on the persistent partition, mode 0600, where Kairos keeps the keys it generates. Neither is encrypted unless the cloud-config has Kairos encrypt those partitions. The plan, the JSON report and the log show fingerprints only. Booting the installed system with `rd.kairos.debug` added by hand writes them to its logs too, as kairos-agent then logs the whole configuration on every boot.

## Cloud datasources

On every boot until it finds some, the image looks for user-data the way cloud-init does: on a NoCloud seed (`cidata`), on a config drive, and from the metadata services of the major clouds and of MAAS. Once it finds some, it stores it in `/oem/95_userdata` and applies it on every boot after. On a cloud VM or a provisioned machine that is the user-data written for the replaced system, and it can create users with an empty password (see [Usage](#usage)). So boot-to-kairos creates `/oem/95_userdata` empty during the install, which stops the image from looking. To have Kairos look for user-data as it otherwise would, declare a stage with a `datasource` in the cloud-config, with the providers you want; that, or a stage writing under `/oem/95_userdata`, keeps it on. The plan says which.

## Tested

- Ubuntu 24.04 cloud image on QEMU with OVMF: UEFI, Secure Boot off, a 20 GiB virtio disk and an active swap file on the root filesystem. Target was Hadron v0.5.1 with Kairos v4.3.0. Kairos came up in active boot on the first reboot and accepted the SSH key from the cloud-config.
- Ubuntu 24.04 cloud image on QEMU with SeaBIOS: legacy BIOS, a 20 GiB virtio disk and an active swap file on the root filesystem, same target. Kairos came up in active boot on the first reboot, in legacy BIOS mode, from a disk with a `bios_grub` partition, and accepted the SSH key from the cloud-config.
- The same as the first, with the network carried over and DHCP off: one NIC at a static address, renamed `lan0` on Ubuntu, with an extra route, MTU 1400, a nameserver and a search domain; and an active-backup bond of two NICs at a static address. SSH reached the VM only at that static address, and Kairos came back there, the NIC found by its MAC under its new name, the bond with its mode, primary port and MII interval, and the routes, MTU and DNS in place.
- The same as the first, installed from an `oci-archive:` copy of that image, made with `skopeo copy --all`, on a VM whose network let only SSH in: connections out of it, by name or by address, failed before the install. Kairos came up in active boot as above.
- The same as the first, with the identity carried over and a cloud-config without any SSH key: Kairos came back under the old hostname, with the same ed25519 and RSA host key fingerprints, and `ubuntu` logged in with its old key under strict host key checking against the `known_hosts` taken before the install. With only root holding a key and no cloud-config, the same key logged in as `kairos`.
- The same as the first on a 6 GiB VM with `--workdir` on an ext4 filesystem of a second virtio disk. Shmem in `/proc/meminfo`, sampled about every 0.1 s, peaked at 329 MiB, the disk image took 1483 MiB of the second disk, and nothing was left on it after the reboot. Kairos came up in active boot as above. `--workdir` on the target's root filesystem and on a vfat filesystem of the second disk were refused before anything was downloaded.
- Ubuntu 24.04 arm64 cloud image on QEMU `virt` with AAVMF: UEFI, Secure Boot off, 4 GiB of RAM, a 20 GiB virtio disk and an active swap file on the root filesystem. QEMU emulated the CPU under TCG on an arm64 host without KVM, so the run's timings say nothing about real hardware. Target was `quay.io/kairos/hadron:v0.5.1-core-arm64-generic-v4.3.0`. The dry run passed and left the disk as it was. Kairos came up in active boot on the first reboot, `uname -m` reported `aarch64`, and the firmware booted the `Kairos` entry, which loads `\EFI\BOOT\BOOTAA64.EFI` from the new EFI system partition. CI has no arm64 runner, so arm64 is tested only by hand, like this.
- Ubuntu 24.04 cloud image on QEMU with OVMF, Secure Boot on with Microsoft's keys enrolled (`OVMF_CODE_4M.secboot.fd` and `OVMF_VARS_4M.ms.fd`), on a 6 GiB VM. `quay.io/kairos/hadron:v0.5.1-core-amd64-generic-v4.3.0` was refused with class `secure-boot`, in the dry run and in the real run, as its `BOOTX64.EFI` is not signed, and the first 64 MiB of the disk read back unchanged. An Ubuntu 24.04 image built with kairos-init v4.3.0, installed from an `oci-archive:` with `--workdir` on a second disk and with `--keep-identity=false`, as the image has an `ubuntu` user of its own, passed the check: the shim chains to the Microsoft Corporation UEFI CA 2011 in db, and GRUB and the kernel to Canonical's certificate in the shim. Kairos came up in active boot, with Secure Boot on.
- The same as the first, with the image's signature verified and named in the plan. Dry runs against a registry on the VM, each before any layer was downloaded and with the disk left as it was, refused the v4.2.0 release with its own signature under the v4.3.0 tag (`bad-signature`), the v4.3.0 image with a layer added (`no-signature`), and that image with v4.3.0's signature bundle attached to it (`bad-signature`), and accepted a copy of v4.3.0 with its signature. With the VM's network closed, an `oras copy --recursive` archive verified with `--trusted-root` and failed without it, and a `skopeo copy` archive was refused as unsigned and accepted with `--verify-signature=false`.
- The same as the first on an NVMe disk, QEMU's NVMe controller with 512-byte sectors, instead of virtio. Kairos came up in active boot as above.
- The same as the first with the root filesystem on LVM: the ESP and an ext4 `/boot` on partitions, and the root filesystem and a 1 GiB swap volume on linear logical volumes over the third partition. The swap volume and the swap file were both turned off, and Kairos came up in active boot as above.
- The same as the first with the root filesystem on LUKS2 over the third partition, opened from the initramfs with a key file; with LUKS2 the dm-crypt table names the key in the kernel keyring. Kairos came up in active boot as above. With LUKS1 instead, whose table carries the key itself, the installer was left waiting at its prompt after it had read that table: a scan of its memory found no copy of the key, while the same scan found the SSH key of the cloud-config it had read.
- Debian 12 and Rocky Linux 9 cloud images, otherwise as the first, with a static address, a default and an extra route, MTU 1400, a nameserver and a search domain on one NIC, and DHCP on a second: Debian once through netplan and systemd-networkd and once through ifupdown and dhclient, Rocky through NetworkManager, with SELinux enforcing and XFS filesystems. Kairos came back with the first NIC as configured and the second on DHCP, and the old user logged in under strict host key checking.

## Limitations

- The cloud-config's install-time stages run inside the build with the host's real devices visible. A stage that acts on the target disk acts on the running system, before anything is quiesced.
- The Secure Boot check looks at who signed a binary, not at the signature: it does not verify that a signature covers the binary's hash, so a binary changed after it was signed passes and is refused at boot. It does not read SBAT revocation levels, nor whether shim validation was turned off with `mokutil --disable-validation`, which boots a GRUB or kernel the check refuses, or shim was told to ignore db with `mokutil --ignore-db`, which refuses one the check lets through db. `MokListRT` also carries the vendor certificates of the shim the running system booted through, which the installed shim may not trust, so a GRUB or kernel signed only by one of those passes the check and is refused at boot. Only the default path is checked: the fallback loader, the GRUB beside it and the image's `/boot/vmlinuz`. A certificate in db or `MokListRT` that cannot be parsed is left out with a warning, and one in a list that revokes stops the install.
- On legacy BIOS, a target disk whose logical sectors are not 512 bytes is refused: legacy firmware commonly cannot boot from one, and SeaBIOS does not even list it.
- On UEFI, a target disk with 4096-byte logical sectors is refused once the disk image is built, before the disk is touched, as long as the image's `kairos-agent` formats its EFI system partition the way v4.3.0 does. It formats it FAT32, and on such a disk the 64 MiB partition holds fewer than the 65525 clusters FAT32 must have. Linux mounts it all the same, but EDK2's FAT driver, which OVMF and most UEFI firmware carry, refuses it, so the machine would find nothing to boot. Asking for a 260 MiB partition with `install.partitions.efi.size: 260` does not help: the agent's `mkfs.vfat` then picks 32 KiB clusters and ends up with 8317. With such clusters it would take about 2 GiB to reach 65525; that size has not been tried. The installer reads the partition the build made, counts its clusters the way EDK2 does, and refuses with class `bad-image`, so an image whose installer gets this right is not refused.
- A `docker save` archive from before Docker 25, without an OCI `index.json`, is refused. Docker 25 replaced that format with the OCI layout read here; convert an older archive with `skopeo copy docker-archive:FILE oci-archive:FILE`.
- A `--workdir` on a filesystem on a loop device backed by a file is refused even when that file is on another disk, and one on NFS or another network filesystem is refused even with a reliable network: neither can be told safe from what the kernel shows. A SAN disk reached over Fibre Channel or SAS, on the other hand, looks like a local SCSI disk and is accepted, though a broken link to it during the write leaves the disk half written too.
- `--disk` must be a physical disk. An LVM volume, an md array or a loop device is refused: the firmware cannot boot from a disk image inside one.
- Some layouts are refused before anything is downloaded: any ZFS mount, because sysfs does not tell which disks a pool is on; a target disk under an md array, bcache or any device-mapper target other than linear, striped, crypt and multipath (LVM cache and thin pools, snapshots, RAID, integrity, VDO), because those may write to it on their own whatever is frozen; a filesystem on the target disk that is mounted only inside a container or another mount namespace; a process, such as a virtual machine, that has a device of the target disk open for writing; and any host partition already carrying a name or filesystem label kairos-agent may use (efi, oem, recovery, state, persistent, COS_*, and whatever the cloud-config's `install` section names), because the agent finds the partitions it formats and mounts by those, not on the disk it was given. Only namespaces that have a running process are seen; one kept open without a process, as snapd does, is not. A swap file whose size does not match what the kernel reports for it, which a swap header smaller than the file or a filesystem block smaller than a page can cause, is refused as possibly not the active one; recreate it with `mkswap` to proceed. A cloud-config that sets `install.firmware` to a mode other than the one the system booted in is refused, as the installed system would not boot. The agent adds an `install` section of its own, with the `device` and `source` it is given, and reads the result through a parser that keeps one of two keys differing only in case at random and nests dotted keys, so a cloud-config that spells `install` other than so, sets a dotted `install.` key at the top level, or has a key under `install` that is not lowercase or holds a dot, is refused. A `config_url` in the cloud-config, which the agent would fetch and merge, is refused too, as it cannot be checked: put that configuration in the cloud-config itself. So is a cloud-config with content in more than one YAML document: the agent reads only the first and drops the rest.

## CI

Every push and pull request is built, vetted, linted with golangci-lint and the repository's `.golangci.yml`, and tested with `-race`. It is also built and vetted for macOS, so that a Linux-only import cannot break development there unnoticed. The tests that need root, which attach loop devices and create device-mapper devices, run through `sudo` on the throwaway GitHub-hosted runner, and the job fails if any test is skipped. An end-to-end job boots a throwaway Ubuntu VM with an active swap file on the runner's KVM, once with UEFI and once with legacy BIOS, first runs a dry run that must pass and leave the start, the end and the partition table of the disk as they were, then replaces it with Kairos, without carrying the identity over, and passes only if the machine comes back in active boot with the cloud-config's SSH key and has applied none of the user-data on the VM's still attached NoCloud seed. The identity carry-over is not booted in CI, as the VM's own user would come back with it and hide an account the seed made; it is covered by the runs under [Tested](#tested). Once all of that passes, the same run builds the release binaries and checks that they are static and report their version. On a pushed `v*` tag it then publishes them as a GitHub release, so nothing is published that the run did not test.
